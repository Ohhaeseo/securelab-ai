# 0004. 요청 제한·로그인 보호와 Redis 장애 정책

- 상태: 채택
- 날짜: 2026-11-20

## 배경

SEC-03(로그인 반복 실패)과 SEC-04(과도한 호출)를 막아야 한다. 기획서는 Redis로 기간별 요청 횟수와 잠금 상태를 관리하고, "요청 제한 실패 시 정책(허용/거부)을 결정하고 기록"하라고 한다.

## 결정

### API 요청 제한 (SEC-04)

- **고정 윈도우 카운터.** 키마다 첫 요청 때 윈도우(기본 60초)가 시작된다. `INCR`과 만료 설정을 Lua 스크립트 한 번으로 처리해 만료 없는 키가 남지 않게 한다.
- 대상: `/api/**`. 로그인 사용자는 **사용자 ID별**(기본 120회/분), 익명 요청은 **IP별**(기본 60회/분)로 센다. `/actuator/health`는 세지 않는다.
- 위치: Spring Security 필터 체인 안, 세션 인증을 읽은 직후·CSRF/인가 검사 전. 거부되는 요청(403, 404)도 한도에 포함된다.
- 초과 시 `429 RATE_LIMITED` + `Retry-After`(윈도우 남은 초). 응답에 `X-RateLimit-Limit`·`X-RateLimit-Remaining`을 넣는다.
- 보안 이벤트 `RATE_LIMITED`는 **윈도우마다 처음 한 번만** 기록한다. 공격 중 차단 응답마다 DB에 쓰면 그 자체가 부하가 되기 때문이다.

### 로그인 보호 (SEC-03)

- 실패 횟수를 두 키로 센다: **(계정 다이제스트 + IP)** 와 **IP**. 기본 15분 동안 각각 5회, 20회를 넘으면 그 키의 남은 시간 동안 로그인을 막는다 (`429 LOGIN_TEMPORARILY_BLOCKED` + `Retry-After`).
  - 계정만으로 막으면, 공격자가 남의 계정을 일부러 잠가 정상 사용자를 막을 수 있다(오탐). 계정+IP 조합으로 막으면 다른 IP의 정상 사용자는 영향을 받지 않는다.
  - IP 키는 한 IP에서 여러 계정을 시도하는 크리덴셜 스터핑을 막는다.
- 차단 중인 요청은 비밀번호를 검증하지 않는다(Argon2 계산 비용을 아낌). 로그인에 성공하면 (계정 + IP) 카운터를 지운다.
- 모든 시도는 `login_attempts`에 기록한다. 이메일은 서버 비밀키로 만든 **HMAC-SHA256 다이제스트**로만 저장한다 (I-5).

### Redis 장애 시 정책

| 대상 | 정책 | 이유 |
| --- | --- | --- |
| API 요청 제한 | **허용 (fail-open)** + 경고 로그 | 일반 API 가용성을 우선한다. 인가는 요청 제한과 별개로 항상 동작한다. |
| 로그인 보호 | **DB 대체 집계** | 로그인은 무차별 대입의 표적이라 열어 둘 수 없다. 모두 막으면 정상 사용자도 로그인할 수 없다. `login_attempts`에서 최근 실패 수를 세어 같은 기준으로 판정한다. |

- Redis 타임아웃은 500ms로 짧게 둬 장애 때 요청이 오래 묶이지 않게 한다.

## 검토한 대안

- **슬라이딩 윈도우 로그(정렬 집합):** 경계 순간에 한도의 2배까지 몰리는 고정 윈도우의 약점이 없지만, 요청마다 기록이 쌓여 메모리·연산 비용이 크다. 실험 목적에는 고정 윈도우로 충분하고, 경계 효과는 실측에서 확인한다.
- **토큰 버킷:** 순간 몰림을 부드럽게 허용하지만 구현·설명이 복잡하다. 이후 필요하면 Lua 스크립트만 바꾼다.
- **계정 단독 잠금:** 구현은 단순하지만 남의 계정을 잠그는 서비스 거부가 쉽다.
- **로그인 보호도 fail-open:** Redis를 끊으면 무차별 대입이 풀리는 우회 경로가 생긴다.

## 결과

- 여러 IP로 나눈 분산 대입(계정당 IP마다 4회씩)은 막지 못한다. 계정 단위 상한을 높게(예: 100회/15분) 추가하는 것은 오탐과 함께 측정한 뒤 정한다.
- 프록시 뒤에 두면 모든 요청이 프록시 IP로 보인다. 로컬 전용이라 `X-Forwarded-For`는 믿지 않는다. 배포 구성이 생기면 신뢰할 프록시를 지정해야 한다.
- 테스트는 모두 127.0.0.1에서 요청하므로, 공통 테스트 설정은 한도를 크게 두고 한도 동작은 전용 테스트에서 작은 값으로 확인한다.
