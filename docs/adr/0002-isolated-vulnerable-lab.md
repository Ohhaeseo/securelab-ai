# 0002. 취약 실험 대상을 별도 앱으로 격리

- 상태: 채택
- 날짜: 2026-11-20 (제안) → 2026-11-20 (채택)

## 배경

"보안 적용 전후" 비교를 하려면 방어가 빠진 취약 버전이 필요하다. 기획서는 취약 로직을 일반 API의 feature flag로 열지 말고 격리된 테스트 전용 앱·컨테이너에 두라고 한다. 처음 저장소 구조에는 그 자리가 없었고, `experiment_runs.defense_enabled=false` 실험을 어디서 돌리는지도 정해지지 않았다 (I-1).

## 결정

- 취약 버전은 `experiments/api-security/vulnerable-api/`에 **별도 Gradle 프로젝트·별도 Spring Boot 앱**으로 둔다. 본 `backend` 빌드 산출물에는 들어가지 않고, 코드도 공유하지 않는다.
- 본 `backend`는 언제나 보호 버전이다. 방어를 끄는 설정을 두지 않는다.
- **대조군 원칙:** 인증 방식(세션 쿠키, CSRF 쿠키→헤더, 로그인 시 세션 ID 교체)과 API 경로·요청 형식은 보호 버전과 같게 하고, **인가 검사만** 일부러 뺀다. 그래야 결과 차이를 인가 결함 하나로 설명할 수 있다.
  - SEC-01: 문서 조회·수정·삭제에 소유권 검사가 없고, 목록이 남의 비공개 문서까지 돌려준다.
  - SEC-02: `/api/v1/security/**`에 역할 규칙이 없다.
- 저장소는 **메모리**(DB 없음)다. 재시작하면 데이터가 사라지고, 본 DB와 섞이지 않는다.
- **루프백 전용:** 기본 포트 `127.0.0.1:18080`. `server.address`가 루프백 주소가 아니면 기동하지 않는다.
- AI 시나리오의 방어 OFF 비교(정책 게이트 없는 naive agent)는 5~6주차에 테스트 코드 또는 이 앱에 추가한다.
- 실험 관리 API(`/api/v1/scenarios`, `/api/v1/experiments`)는 본 `backend`의 `lab` 프로필에서만 빈을 등록하고 관리자 역할을 요구한다 (I-6).

## 검토한 대안

- **본 API에 feature flag:** 구현은 가장 쉽지만, 설정 실수 하나로 운영 코드에 취약점이 열린다. 기획서 원칙에 어긋난다.
- **같은 앱의 별도 프로필(`vulnerable`):** 코드가 같은 산출물에 들어가므로 flag와 위험이 비슷하다.
- **Gradle 멀티 프로젝트로 공통 엔티티 공유:** 중복은 줄지만 두 앱이 엮인다. 취약 앱에 필요한 기능은 작아서 따로 써도 부담이 작다.
- **취약 앱도 PostgreSQL 사용:** 지연 비교는 더 공정하지만, 본 DB 오염 위험과 설정 부담이 생긴다. 지연 비교는 보호 버전의 정책 적용 전후(8주차 k6)로 따로 잰다.

## 결과

- 두 앱의 응답 시간 차이에는 저장소 차이(메모리 vs PostgreSQL)가 섞인다. SEC-01/02 비교에서는 공격 성공률을 주 지표로 쓰고, 지연은 참고 값으로만 기록한다.
- 시나리오 러너(`experiments/api-security/runner`)는 대상 주소를 인자로 받아 두 앱에 같은 요청을 보낸다.
- 취약 앱에는 "결함이 계속 재현되는지" 확인하는 테스트를 둔다 (취약점이 실수로 고쳐지면 대조군이 사라지므로).
