# 0002. 취약 실험 대상을 별도 앱으로 격리

- 상태: 제안 (3주차 시작 전 확정)
- 날짜: 2026-11-20

## 배경

"보안 적용 전후" 비교를 하려면 방어가 빠진 취약 버전이 필요하다. 기획서는 취약 로직을 일반 API의 feature flag로 열지 말고 격리된 테스트 전용 앱·컨테이너에 두라고 한다. 그런데 저장소 구조에는 그 자리가 없고, `experiment_runs.defense_enabled=false` 실험을 어디서 돌리는지도 정해지지 않았다.

## 결정 (제안)

- 취약 버전은 `experiments/api-security/vulnerable-api/`에 **별도 Spring Boot 앱**으로 둔다. 본 `backend` 빌드 산출물에는 들어가지 않는다.
- 본 `backend`는 언제나 방어가 켜진 보호 버전이다. 방어를 끄는 설정을 두지 않는다.
- 취약 앱은 Docker 내부 네트워크나 `127.0.0.1`에서만 열린다.
- 방어 OFF 실험:
  - **SEC 시나리오:** 같은 요청을 `vulnerable-api`와 `backend`에 각각 보내 비교한다.
  - **AI 시나리오:** 정책 게이트 없이 도구를 바로 실행하는 naive agent를 테스트 코드(또는 `vulnerable-api`)에만 두고, 본 `backend`의 정책 게이트와 비교한다.
- `experiment_runs`에는 `target`(VULNERABLE/PROTECTED)을 남긴다.

## 검토한 대안

- **본 API에 feature flag:** 구현은 가장 쉽지만, 설정 실수 하나로 운영 코드에 취약점이 열린다. 기획서 원칙에 어긋난다.
- **같은 앱의 별도 프로필(`vulnerable`):** 코드가 같은 산출물에 들어가므로 flag와 위험이 비슷하다.
- **Gradle 멀티 프로젝트로 공통 엔티티 공유:** 중복은 줄지만 취약 앱과 본 앱이 엮인다. 취약 앱이 필요한 기능은 문서 조회 몇 개라 복사해도 부담이 작다.

## 결과

- 취약 앱에 최소 기능(로그인, 문서 조회·수정, 관리 API 일부)을 따로 구현해야 한다.
- 두 앱이 같은 DB 스키마를 쓸지, 취약 앱이 자체 DB를 쓸지 3주차에 정한다. 권장은 별도 DB(또는 별도 스키마)다.
- 실험 러너는 대상 주소를 설정으로 받는다.
