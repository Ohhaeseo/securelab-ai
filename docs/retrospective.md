# 회고 (2026-11-21)

8주 로드맵을 앞당겨 진행해 1~7주차와 8주차 측정·문서까지 마쳤다. 남은 것은 시연 영상 녹화다.

## 잘된 점

- **대조군 설계.** 취약 앱(`vulnerable-api`)의 인증·CSRF·세션 처리를 보호 버전과 같게 두고 인가만 뺐다. 그래서 "ASR 100% → 0%"를 인가 결함 하나로 설명할 수 있었다.
- **결과로 판정.** 응답 코드가 아니라 본문 marker 노출, 변경·삭제 반영, 실제 도구 실행으로 침해를 셌다. 보호 버전의 목록 API는 200을 돌려주지만 침해 0건이라는 것을 정확히 구분할 수 있었다.
- **모델 반응과 실제 행위의 분리 (I-2).** AI 벤치마크에서 소형 모델은 23~70% 넘어갔지만 실제 행위는 0%였다. 두 수치를 따로 기록했기 때문에 "프롬프트 방어는 부족하고 서버 정책이 마지막 방어선"이라는 결론을 수치로 말할 수 있다.
- **실제 HTTP 통합 테스트.** 쿠키 속성(SameSite, HttpOnly), 세션 ID 교체, CSRF 재발급처럼 MockMvc로는 놓치기 쉬운 동작을 실제 서버와 쿠키 저장소로 확인했다.
- **결정 기록.** ADR 6개와 자율 결정 기록으로 "왜 이렇게 했는가"를 남겼다.

## 아쉬운 점과 실수

- **측정 도구를 의심하는 데 시간이 걸렸다.** k6 첫 측정에서 오탐률 92%가 나왔는데, 원인은 정책이 아니라 k6가 반복마다 쿠키를 비우는 기본 동작이었다. 기대와 크게 다른 결과는 도구부터 확인해야 한다.
- **테스트 도구의 부작용.** spring-security-test의 `csrf()`가 공유 컨텍스트의 CSRF 저장소를 바꿔 다른 테스트를 깨뜨렸다. 처음부터 실제 HTTP 클라이언트로 갔다면 시간을 아꼈을 것이다.
- **같은 PC의 다른 프로젝트.** 개발 포트 8080을 다른 프로젝트와 같이 써서, 실험 요청이 엉뚱한 서버로 간 일이 있었다. 공격 도구를 다룰 때는 대상 확인을 기본으로 넣어야 한다 — 지금은 전용 포트 + 대상 확인을 한다.
- **Windows 환경 함정.** PowerShell 5.1의 한글 스크립트 인코딩(BOM), `--args` 따옴표, 응답 한글 표시 문제에 시간이 들었다.
- **지연 비교의 정밀도.** OFF/ON을 한 번씩 순서대로 쟀다. 여러 번 번갈아 재고 신뢰 구간을 내야 정책 비용을 확정적으로 말할 수 있다.

## 다음에 할 일

1. 시연 영상 녹화 ([시연 대본](demo-script.md)).
2. k6 OFF/ON을 3회 이상 번갈아 재서 지연 차이의 변동 범위 확인 (지금은 2회: p50 +1.2~2.5ms, 꼬리 지연은 잡음이 더 큼).
3. 요청 제한: 반복 위반자에게 더 긴 차단(점진적 제재) 추가 후 차단률 재측정.
4. 로그인 보호: 여러 IP로 나눈 분산 대입을 막는 계정 단위 상한(높은 값) 추가와 오탐 측정.
5. AI: 더 큰 모델(3B 이상)과 다른 문맥(이메일, 위키)으로 AI-01 반응률 비교. 쓰기 도구를 넣는다면 사용자 확인 단계를 먼저 설계(ADR-0005).
6. 관리자 API의 개별 작업 권한(관리 쓰기 작업이 생길 때).
